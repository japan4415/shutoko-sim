# ルート探索設計

## 探索問題

[原案](original.md)の「首都高を一周したうえで1区間先で降りると1区間分の料金になる」を前提に、その走り方が時間予算に収まる経路を探す。単なる最短経路や、任意の出口へ抜ける長距離経路は対象ではない。

出発地点 `s`、時間下限 `L`、上限 `U` に対して、方向付き入口 `i` とその1区間先の利用可能な出口 `o` の検証済みペアを選ぶ。一般道で入口へ向かい、首都高を一周し、出口 `o` で降りる。出口から一般道で `s` へ戻ることは今回の企画提案で、首都高上の一周とは区別する。

## 実走行経路と料金の関係

```text
実走行: 出発地点 → 一般道 → 入口 → 基準点 → 一周 → 同じ基準点 → 1区間先の出口 → 一般道 → 出発地点
課金対象: 入口 → 1区間先の出口（実走行の一周分を加算しない）
```

「1区間先」は緯度経度の近さや出口番号の加算では決めない。方向・接続・課金条件を確認した `billingPair` で指定する。一周は、そのペアに定義した本線の基準点へ、同じ進行方向で戻る非空の有向閉路と定義する。単に道路名が環状線であることや、一般道で出発地へ戻ることを一周とは数えない。この形式化は初期版の実装定義であり、対象にできる一周の種類は実経路検証で調整する。

[首都高の料金距離説明](https://www.shutoko.jp/fee/fee-info/pay_etc/distance/)は、複数経路がある場合に入口出口間の首都高最短経路を料金距離とする原則を示している。具体的なペアの料金と利用条件は別途確認し、実走行距離へ単価を掛けて料金を計算しない。

## 時間条件

内部では秒を使う。

```text
T_shutoko = T_entry_to_anchor + T_loop + T_anchor_to_exit
T_base = T_access + T_shutoko + T_return
buffer = max(300, ceil(T_base * 0.20))
T_plan = T_base + buffer
採用条件: L * 60 <= T_base かつ T_plan <= U * 60
```

5分または20%の余裕は仮値で、交通予測の信頼区間ではない。「推定時間」は `T_base`、「余裕込みの計画時間」は `T_plan` と呼ぶ。表示は切り上げた分、採否は丸め前の秒を用いる。休憩は含めない。`L = U` など余裕を確保できない入力は有効だが候補なしになり得る。

## 道路グラフ

ノードは交差点・ランプの接続点、エッジは方向付き走行区間。高架と一般道、入口と出口、JCT の分岐、一方通行、車両制限、禁止遷移を保持する。地理的な交差だけで接続しない。探索状態は直前エッジと制限の判定に必要な履歴も持ち、基準点への帰還時にも遷移を検証する。

一般道の往復もグラフに含める。出発点は車両通行可能な一般道へ投影し、高速道路本線へ直線接続しない。暫定200m以内に有効な接続がない場合や、データ境界で帰路が切れる場合は対応範囲外とする。投影前後の位置を表示し、建物内や私有地から道路までの移動が未モデル化であることを確認できるようにする。

正しく解釈できない時間依存・複雑な通行制限を持つ区間は初期データから除外する。区間時間は検証した静的モデルを使い、欠損時は道路種別ごとの保守的な値と欠損フラグを用いる。制限速度だけで実所要時間を断定しない。モデル値・版をデータに含め、代表区間で確認する。

## 探索手順

1. **出発地点の空間スナップ**: リクエストが座標（`origin: { lat, lon }`）の場合、WASM 内で Local エッジに接する全ノードを対象に等距円筒近似（Equirectangular approximation、東京付近 `cos(lat)` 補正）で線形走査する。最近傍ノードとの距離が `SNAP_RADIUS_METERS`（200m）以内の場合はそのノードを出発地点 `s` とし、`snappedOrigin` に記録する。200m を超える場合は探索を行わず `status: "no_candidates"`, `reason: "NO_CONNECTION"` を返す。`originNodeId` が直接指定された場合は距離 0m としてそのノードを採用する。
2. 出発地点 `s` から一般道（Local エッジ）のみを辿る Forward Dijkstra を実行し、全課金ペアの入口エッジへの最短時間合法経路（access）を一括探索する。目標入口エッジへの遷移時（最後の Local エッジ → entry エッジ）も探索の中で禁止遷移列と照合し、違法な接続を回避する。
3. Forward で到達可能な各課金ペアの出口エッジを起点履歴に持つ状態から一般道（Local エッジ）を辿る Return（Backward）Dijkstra を実行し、出発地点 `s` への最短時間合法帰路（returns）を探索する。起点となる出口エッジから最初の Local エッジへの遷移も探索の中で禁止遷移列と照合する。
   - Dijkstra の状態は禁止遷移（`forbidden_transitions`）の健全な枝刈りのため `(node, 直近 L-1 本のエッジ ID 列)` をキーとする Suffix-based Dijkstra とする（`L` は禁止遷移の最大長）。同じ `(node, suffix)` に到達した 2 経路の将来の合法性は完全に同一となるため、最短路が禁止遷移で違法となった場合でも、次の合法な最短路が必ず採択される。
   - 優先度キューのタイブレーク順序は `(duration_seconds, distance_meters, edge_id, node, suffix)` の完全順序とし、浮動小数点数を用いず完全な決定論を保証する。
4. Forward / Backward の両方で合法な経路が得られた検証済み `billingPair` のみを対象とし、一般道が接続していないペアは早期スキップする。
5. 各ペアの基準点（アンカー）から同じ基準点へ戻る閉路を探索する。基準点以外のノードを同一閉路内で再訪しない制約とし、一周のみを生成する。空閉路を禁止する。
6. 入口から基準点、閉路、基準点から出口、および一般道往復を結合する。閉路以外の接続部分と閉路のエッジが重なることは許すため、経路全体に「同じエッジ再訪禁止」を適用しない。
7. 全体の方向・禁止遷移、一度の入場と退出、1区間先の出口、一周の成立、時間条件を再検証する。
   - 時間窓の意味論: 一般道の access / return は最短時間合法経路 1 本となるため、最短経路の組合せで所要時間が `minMinutes` を下回る場合は候補とならない（従来の複数パス列挙による冗長経路での下限充足は行わない）。
8. **幾何合成と Google マップ引き継ぎ**:
   - **GeoJSON LineString 合成**: 全経路（access → loop → return）のエッジ列に対し、先頭エッジの `from` ノード座標、以降各エッジの `to` ノード座標を `[lon, lat]` として順次連結し、端点の重複のない単一の LineString 座標列を生成する（座標点数 = エッジ数 + 1）。
   - **通過路線名の抽出**: 首都高本線・ランプ部分で通過したエッジの `name` を重複除去した順序付きリスト `roadNames` として生成する。
   - **Google Maps URLs 生成と暫定経由地選定**: 出発地点と帰着地点を `snappedOrigin`（入力 `origin` があればそちら）とし、`select_waypoints` で最大3点の経由地を選定して URL を構成する。URL 長が 2,048 文字を超える場合は `NO_HANDOFF` として候補を除外する。

### Google マップ引き継ぎの暫定経由地選定ルール（#8 依存）

Google マップ上でのナビゲーションにおいて、一周を短絡（ショートカット）せず周回を維持するため、`crates/routing-core/src/handoff.rs` の `select_waypoints` に暫定ルールを分離・カプセル化している:
1. **入口合流直後の本線ノード**（課金ペアの `anchorNodeId`）
2. **周回の距離中点ノード**（loop 内の累積距離が 50% に最も近いエッジの `to` ノード）
3. **出口分流直前の本線ノード**（出口エッジの `from` ノード）

> [!IMPORTANT]
> このルールは issue #8（実機検証 spike）の物理端末検証結果に基づいて差し替える前提の暫定実装である。候補の `warnings` には必ず `HANDOFF_WAYPOINTS_UNVERIFIED` が含まれる。

本線閉路（loop）の探索は訪問履歴を持つ幅制限探索とし、残り帰還時間の下界と退出・一般道帰路の時間を用いて、上限内で帰れない状態を枝刈りする。訪問履歴の異なる状態を同一ノードの最短時間だけで統合しない。本線 loop の探索においては、最短経路1本では時間下限を満たす周回候補を作れない。

既定値は深さごとの保持状態200、全ペア合計の展開状態100,000、閉路の最大エッジ数2,000とする。一般道探索の Dijkstra 化（Forward 一括探索および到達可能 exit 起点の Return 探索）により、実データ（8課金ペア、約1万エッジ）での全展開数は約20,000〜57,000展開（release 所要時間約0.85秒）に収まり、既定上限100,000の範囲内で安定して動作する。いずれかの上限到達は `truncated` とし、検証済みの候補だけ返す。UI は探索開始10秒で Web Worker を終了でき、その場合は候補を返さず再試行を案内する。同じ入力・成果物版・探索上限では同じ展開順と結果にする。

## コスパの評価

最初に「一周後に1区間先で退出」という必須条件で絞る。1区間だからすべての入出口ペアが同額とは仮定しない。

金額が確認済みの候補同士は `首都高走行秒数 / 料金円` の大きい順、同値なら首都高時間が長い順、一般道時間が短い順、安定 ID 順にする。無料等で料金0円のデータは初期対象に含めず別途扱いを設計する。

料金額が未確認なら比率は計算しない。同じ課金ペア内では首都高時間の長い順で比較できる。異なるペアをまたぐ場合は、金額比較ができないことを明示して時間基準の暫定推薦とする。検索候補集合に未確認額がある場合は集合全体をこの時間基準に切り替え、確認済みだけを不当に優先しない。全候補で金額が確認できた場合だけ金額あたりの比較を使う。「一番」は探索した候補集合内の順位であって、全経路の最適保証ではない。

多様性は首都高有向エッジの距離加重 Jaccard 類似度（共通エッジ距離 / 和集合エッジ距離）で確認する。選出済み候補との類似度0.8以上を除き、少なければ水増ししない。重複エッジはこの類似度では1回、実走行時間・距離では通過回数分を数える。この `time_per_yen` ランキング（同額なら首都高走行時間が長い候補を優先）と重複除外の仕様により、時間上限 `maxMinutes` が広い場合、近傍の他ペア上位候補（例えば芝公園起点での霞が関入口発ルートなど）によって自ペア候補が置き換わり除外されることがある。そのペア本来の周回候補を得るには、計画時間が収まる適切な `maxMinutes` を指定する。

## 検証

人工グラフで空閉路、基準点への帰還、帰還時の禁止遷移、入口から出口への短絡、間違った1区間先、二周、途中退出・再入場を検出する。接続区間と一周部分の重複を誤って落とさないことも確認する。小規模では全列挙した閉路と比較し、探索打ち切りによる候補欠落と不正経路を区別する。

実データでは方向別入出口ペア、一周の道路列、JCT、高架、データ境界を人手でも検証する。通行可能性と課金ペアの確認は別項目とし、どちらかが未確認なら公開候補に使わない。
